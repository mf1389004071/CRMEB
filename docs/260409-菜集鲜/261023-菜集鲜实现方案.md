### 1.3 定稿时对 v2 的修正（读代码后）
1. **v2 说“到付订单必须豁免超时取消”——代码已豁免**：`StoreOrderDao::getOrderUnPaidList` 排除 `pay_type=offline`，`UnpaidOrderCancelJob` 对 offline 直接返回。无需改。
2. **现有后台订单列表的“待发货/待收货”等标签都要求 `paid=1`**，未支付的 offline 订单只出现在“未支付”下。因此到付订单必须新增**按 `fulfil_status` 的列表入口**，不能指望现有标签。
3. **用户取消**：现有 `cancelOrder` 对 `paid=1` 拒绝、对未支付允许。到付订单未收款即 `paid=0`，所以必须新增“履约状态 ≥ 备货中则禁止用户取消”的判断。
4. **“确认收款”已有**：`OrderOfflineServices::orderOffline`（置 `paid=1`、写 `offline` 状态流水、记资金流水）。直接扩展它作为“收款确认”，补收款人/实收金额/时间。
5. **多语表改为通用表** `eb_i18n_content`（实体类型/ID/字段/语言/值），一张表覆盖商品、分类、规格名、区划名，替代“已确认版”里的 `eb_store_product_lang`（意图相同，扩展性更好）。
6. **运行环境提醒**：后端为 **PHP 7.4**，所有新代码不得使用 PHP 8 语法（`match`、命名参数、`?->`、构造器属性提升、联合类型等）。

## 3. 关键设计要点（摘要，细节见详细设计）

### 3.1 区域分层价
- 价目绑定 `city_id` + `product_id` + 规格 `unique`；取价从当前节点沿 `path` 祖先链**向上**找，命中即用，**不跨兄弟节点**。
- 整链无价 → 看“允许全国价”（系统级默认否 + 商品级；生鲜默认关）：否则不展示、不可加购；是则回落主表价。
- 取价**唯一入口** `RegionPriceServices`；服务端下单重算；切区清购物车。
- 列表过滤用 `path` + `EXISTS`，价格带出后短缓存。
- 一期关闭会员价/活动价/优惠券/积分，避免叠加。

### 3.2 到付订单状态机
```
创建: paid=0, pay_type=offline, status=0, fulfil_status = (cod_auto_stock_up ? 1备货中 : 0待确认)
 待确认(0) --后台确认接单--> 备货中(1) --后台开始配送--> 发货中(2) --送达核销--> 已送达(3)
 收款(独立): 后台“确认收款” → paid=1、记实收金额/收款人/时间
 已送达 且 已收款 → 订单完结(status=3)
 取消: 后台取消（任意未送达状态，回退库存）；用户仅在 fulfil_status=0 时可取消
```
所有变更写 `eb_store_order_status` 并带操作人。

### 3.3 多语
- 界面文案：沿用 `lang_*` 表 + `Cb-lang`；入口处统一规范化语言码。
- 登录用户语种存 `eb_user.locale`；改语：本地 → 服务端 → 刷新。
- 业务内容：`eb_i18n_content`，读取回落链 **当前语 → 默认语(vi-VN) → 主表字段**；订单快照取下单语言。

### 3.4 币种
本位币 VND，区域价/订单只存本位币；展示 `round(base × rate, 小数位)`；订单落库快照币种/汇率/展示金额；统一 `MoneyServices` 与前端 `formatMoney`。

## 5. 风险与对策

| 风险 | 对策 |
|------|------|
| 取价入口遗漏 → 显示价≠结算价 | 唯一入口；下单服务端重算；覆盖单测（区有价/仅市价/仅国价/开关开关/兄弟区） |

## 6. 与客户对齐的关键话术（交付前）

1. 一期只有 H5，Facebook/TikTok 没有微信式小程序，靠链接触达；Zalo Mini App 另立项。

4. 区域价需要客户提供“商品 × 区域 × 价格”表（Excel）。

### 10.1 批注稿 · 项目组逐条答复原文（决策溯源）

#### 10.1.1 业务与范围

1. 一期用户是 **纯 B 端商户**，还是 B+C 都做？是否要「中餐厅」等经营类型标签与推荐？  
   - 都简单为c用户, bc类只是用户性质不一样, 业务流程还是一样的
2. 社区团购：一期是否必须？若必须，团长从哪来、怎么结算？  
   - 不做
3. 现场支付：下单后订单是否 **直接视为有效订单**（跳过待付款），还是保留「待付款-线下」状态由后台确认？  
   - 订单下单就视为有效订单, 订单添加备货中/发货中等状态, 备货中的用户无法取消, 可在线客服或电话管理人员来取消
4. 十几个城市：是否需要 **分城库存**，还是全国/单仓库存 + 仅价格不同？  
   - 不强制, 管理端自己配置, 
5. 无某城报价时：隐藏商品还是显示默认价？  
6. 配送：自营配送为主，还是也要对接越南本地物流单号？  
   - 自营配送
7. VAT：价格是否含税？小票要不要税号？参考图写「未含 VAT」——是否要做价税分离？  
   - 后台商品级可配置税率, 默认0
8. 起送价、配送费、配送时段是否按城市不同？
   - 不强制要求, 可配置

#### 10.1.2 语言与内容

9. 语言码统一用 `vi-VN` 还是 `vi_vn`？（前后端、库表、请求头需单一约定）  
   - 将前端的转换成后端统一的, 后端返回的也做前端适配, 做好兼容, 统一性偏最小改动的一方, 你给我选择建议和佐证
10. 商品多语是否一期就做，还是先主表只填越南语、二期再分表？  
   - 可简单做
11. 谁负责越南语终审？（客户方越南同事 / 外包译员）  
   - 先不考虑这个
12. 是否还要英语作为第三语言（东南亚扩展）？
   - 多语言现在默认考虑 中越英三语

#### 10.1.3 地址与账号

13. 越南地址层级用到哪一级？（省 → 市/县 → 坊/社 是否三级都要）  
   - 最细
14. 区划数据由谁提供？是否接受公开数据源导入后再人工改？  
   - 可谷歌地图采集, 支持导入, 支持人工改
15. 登录方式：手机验证码（需越南短信通道）还是密码 / 仅下单留联系方式？  
   - 不要验证码能力, 简单即可
16. 国别是否一期就要「CN + VN」双国，还是先只做 VN？
   - 要, 直接做到区划里视为国家级的

#### 10.1.4 打印与硬件

### 10.3 已确认版 · 生鲜属性明细（§5A）

面向「蔬菜水果为主、展示中国产品」，在现有商品模型上**最小扩展**，不做独立生鲜中台。

#### 10.3.1 字段与复用

| 属性 | 建议落地 | 说明 |
|------|----------|------|
| **规格** | 复用现有多规格 SKU / 规格名 | 如「箱 / 袋 / 把」；与规格价、区域价 `unique` 对齐 |
| **称重** | `unit_name`（kg/g 等）+ 可选 `net_weight`（净含量数值） | 列表可展示「约 x kg/件」；称重品仍按件下单（简单），不做称重结算秤 |
| **保质期** | 商品字段 `shelf_life_days` 或文案 `shelf_life_text` | 数字天数优先，便于筛选；也可「见包装」类文案 |
| **产地** | `origin`（建议多语：可放商品多语表或主表+译文字段） | 如「中国山东」；华人/越南用户都关心 |
| **冷链** | `need_cold_chain`（0/1）+ 可选 `cold_chain_note` | 详情角标/标签「需冷链」；打印单可带出，提醒配送 |

另建议：`is_fresh`（是否生鲜）开关——为真时上述字段在后台表单展示并前端强调；非生鲜商品可隐藏，避免干扰标品。

#### 10.3.2 实现原则

- **优先加列到 `eb_store_product`（或一张很薄的 `eb_store_product_fresh` 扩展表）**，保证列表筛选/标签好查。  
- 现有 `store_product_param` 参数可作补充（营养成分等），**核心五类不要只靠自由参数**，以免运营乱填、前端难展示。  
- H5：详情固定区块展示；列表可显示产地 + 冷链标 + 单位。  
- 打印/下载单据：生鲜单带出产地、冷链、保质期（有则打）。  
- 旧商品无值：前端不展示空项；不删原字段。

#### 10.3.3 不做（保持简单）

- 不对接温湿度 IoT、冷链轨迹。  
- 不做「按实际称重二次结算」（若客户日后要，另立项）。  
- 不强制所有商品填满生鲜字段（仅 `is_fresh=1` 时关键项可必填，由运营定）。

### 10.4 已确认版 · 区域差异价明细

#### 10.4.1 交互（类多多买菜）

1. 用户进入商城前/首页：**必须先有「当前配送区域」**（定位匹配或手动选择）。  
2. 未选区：引导选区，**不展示有效区域价商品列表**（或空态）。  
3. 顶栏展示当前区域，可切换；**切区提示并清空购物车**（推荐清空，实现简单、无错价）。  
4. 请求带区域标识（建议请求头如 `Cb-region` / 参数 `region_id`，与 `system_city` 节点 id 对齐）。  
5. **开放销售区域白名单（一期必做）**：仅白名单内的市/区（或配置的可选节点）可被选为「当前配送区」，避免任意坊/社可选。  
6. **定位失败兜底（一期必做）**：授权失败/匹配不到 → 展示热门城市（或白名单热门）列表供点选，禁止卡死首屏。

> 说明：本期不做「小区团长」实体；「选区」= 区划树上**已开放**的配送区域节点。若日后做社区团购，可在同选区会话上挂自提点，而不推翻取价模型。

#### 10.4.2 定价颗粒度：国家 / 省 / 市 / 区

与区划树四级（或国+省+市+区）对齐，**商品可配置在某一层级挂价**：

| 概念 | 规则 |
|------|------|
| 价目绑定 | 每条价绑定一个 `city_id`（区划节点）+ `product_id`（+ SKU `unique` 如有） |
| 分层匹配 | 取价时按用户当前选中节点，**自下而上**找价：区 → 市 → 省 → 国家，命中即用 |
| 「设置到哪一级」 | 运营给某商品在「区」挂了价，则用户当前区必须命中该区价（或更精确规则见下）才可售；仅挂在市则该市及下属未单独覆盖的区可用市级价（自下而上已覆盖） |
| 展示条件 | 在用户当前区域路径上 **找不到任何挂价**，且未允许全国价 → **不展示该商品** |

**「设置区则必须有当前定位区域价格」的落地理解（建议写死为产品规则，避免歧义）：**

- 取价只认「从当前节点向上」的价目链。  
- 若某 SKU **存在任意「区级」价目**，且用户当前落在某区：则优先用该区价；若该区无价、仅有其它区的区级价，**不可用其它区的区级价**，继续向上找市/省/国价；若整条链都没有 → 看全国价开关。  
- 市/省级同理：不跨同级兄弟节点借价。

#### 10.4.3 「默认全国价」开关（默认否）

| 项 | 约定 |
|----|------|
| 开关名（示意） | `product_allow_default_price` 或商品级 `allow_national_price` |
| **默认** | **否** |
| 否 | 当前区域价链无命中 → **不展示 / 不可加购** |
| 是 | 无区域价时回落主表 `store_product.price`（全国统一价） |

**建议双层，仍保持简单：**

1. **系统级开关**（默认否）：总闸。  
2. **商品级开关**（默认跟随系统/否）：个别**标品**可开「允许全国价」；**生鲜默认关闭**，减少错价。  

一期按「系统默认否 + 商品级可开」落地即可。

#### 10.4.4 表与服务（示意）

```
eb_store_product_region_price
  id, product_id, unique(sku), city_id, price, ot_price,
  stock nullable,    -- 空=用主表库存；有值=该区域库存（管理端可选配，不强制）
  status, add_time, ...
```

- **唯一取价入口**：`RegionPriceServices`（名称可定），列表/详情/购物车/确认单/改价校验全部走它。  
- 禁止业务里直接读 `store_product.price`（除「允许全国价」回落分支）。  
- 缓存：按 `product_id + city_id` 短缓存；改价清缓存。

#### 10.4.5 库存 / 后台 / 门店运费

- **不强制分城库存**；默认用主表库存；价目表 `stock` 可空；管理端需要时再填区域库存。  
- 商品编辑：「区域价格」；支持按国/省/市/区选节点定价；**Excel 批量导入**（城市多、SKU 多时刚需）；现有单价格字段保留，作全国价回落源。  
- `system_store` 仍只做自提/门店，**不用门店价冒充区域价**。  
- 运费模板按城能力可复用；起送价/配送费/时段：**可配置，不强制**（有配置则校验）。

### 10.6 已确认版 · 多语言 / 多币种明细

#### 10.6.1 语言码约定（建议 + 佐证）

**建议：业务与库表统一用 BCP47 风格，与现网中英一致：`zh-CN` / `vi-VN` / `en-US`。**

| 依据 | 说明 |
|------|------|
| 安装数据 | `eb_lang_type.file_name` 已是 `zh-CN`、`en-US`；`lang_country.code` 同形 |
| 商城前端 | `lang.js` 默认/`fallbackLocale` 为 `zh-CN`；H5 用 `navigator.language`（多为 `vi-VN`） |
| 请求头 | `Cb-lang` 与 `file_name` / 前端 `locale` 对齐成本最低 |
| 反例 | 仓库脚本 `database/add_lang_vi_vn.sql` 使用 `vi_vn`，与中英风格不一致，易导致头与库匹配失败 |

**兼容做法（最小改动）：**

- 库内越南语主数据用 **`vi-VN`**（`lang_type` + `lang_country`）。  
- 若已存在 `vi_vn`：保留行，增加 `vi-VN` 映射，或在读取 `Cb-lang` 时做一次规范化（`vi_vn`/`vi`/`vi-vn` → `vi-VN`）。  
- ThinkPHP `config/lang.php` 已有 `vi-vn`/`vi_vn` 别名，可继续用别名表，**不必改文件包命名大搬家**。  
- 管理后台 Vue 静态包 key 若为 `vi-vn`，仅在 admin 侧做 locale 映射即可。

**结论：统一性偏「已与中英一致的一方」→ `vi-VN`；对历史 `vi_vn` 做兼容层，不删旧数据。**

#### 10.6.2 界面文案与用户语种持久化

- 继续 `lang_code` + `get_lang_json`；站点默认 **越南语**；可切中/英。  
- 机翻 + 后台改词条 + `lang_version`；终审人选本期不阻塞。

**登录态语种规则：**

| 场景 | 行为 |
|------|------|
| 未登录 | 本地缓存 `locale`；无缓存则站点默认 `vi-VN`（可再弱参考浏览器语言，但默认仍偏越语） |
| 已登录 | **以用户上次保存的语种为准**（用户表字段如 `eb_user.locale` / `language`，取值 `vi-VN`/`zh-CN`/`en-US`） |
| 用户修改语言 | ① 写本地缓存 ② **立即调接口保存到服务端** ③ **刷新页面** 使整包文案与商品多语按新语言重载 |
| 登录成功 | 用服务端语种覆盖本地；若服务端为空则把当前本地语种回写服务端 |

实现要点（最小改动）：

- 新增保存语种接口（如 `PUT/POST user/locale`），登录用户信息接口带回 `locale`。  
- 前端改语处（现有 `user_info` 语言选择）接上述三步；未登录仅本地 + 刷新。  
- 请求头 `Cb-lang` 始终跟当前生效 locale。

#### 10.6.3 商品多语

- （已确认版原写 `eb_store_product_lang`；**定稿改用通用表 `eb_i18n_content`**，见 §1.3 / §3.3。）  
- 接口按 `Cb-lang` 取，缺则回落默认语或主表字段；回落链：**当前语 → 默认语(vi-VN) → 主表字段**。  
- 后台商品编辑按语言 Tab 填写；可不上一期做齐所有 CMS，商品优先；分类、规格名、区划名同理（定稿 M5）。

#### 10.6.4 多币种：币种配置

建议表或配置集 `eb_system_currency`（示意）：

| 字段 | 含义 |
|------|------|
| `code` | VND / CNY / USD … |
| `symbol` | đ / ¥ / $ |
| `name` | 多语名称可简单中英越三字段或跟 lang |
| `decimal_places` | VND 建议 0；CNY/USD 建议 2 |
| `thousand_sep` / `decimal_sep` | 展示用 |
| `is_base` | **是否本位币**（全站唯一，建议 **VND**，与越南现场收款一致） |
| `status` / `sort` | 启用与排序 |

后台可增删改启用币种；至少预置 VND、CNY、USD。

#### 10.6.5 多币种：汇率

| 规则 | 约定 |
|------|------|
| 标价/区域价/订单金额 **一律按本位币存储**（VND） | 避免多套区域价再乘币种爆炸 |
| 汇率表 | `base_code` + `quote_code` + `rate`（1 本位 = rate 报价币，或约定统一方向并写死）+ `updated_at` + 操作人 |
| 维护方式 | **后台手工维护**（一期）；不做自动爬虫/银行 API（可预留接口） |
| 改汇率 | 记简单操作日志（可复用系统日志或短表）；**已生成订单不回溯改价** |

#### 10.6.6 多币种：展示规则

| 规则 | 约定 |
|------|------|
| 用户展示币种 | 可切换（本地 + 登录用户可存 `display_currency`）；默认：跟站点/跟当前国家（VN→VND，CN→CNY）可配置 |
| 列表/详情/购物车 | `display = round(amount_base * rate, decimal_places)` + 符号格式化；**同时可次要展示本位币**（开关，默认仅展示币） |
| 下单落库 | 订单存 **本位币应付总额** + 快照 `currency_code`（用户展示币）+ `exchange_rate` + `pay_amount_display`（展示币金额） |
| 打印/后台 | 主显示本位币（收款用）；可附展示币金额，避免现场收款歧义 |
| 与区域价关系 | 先取区域价（本位）→ 再按展示规则换算；取价服务不直接存多币种价 |

#### 10.6.7 多币种：简单优先边界

- **不做**：按币种分别录入区域价、多币种在线支付、自动锁汇、财务多账套。  
- **统一金额工具**：`MoneyServices::format($amountBase, $displayCode)`，前后端约定同一套，禁止页面手写千分位。

### 10.7 已确认版 · 订单 / 支付 / 打印 / 通知 / 审计明细

#### 10.7.1 交易闭环

```
加购 → 确认订单 → 不走在线支付 → 下单成功 = 有效订单
  → 状态进入「备货中」（或等价；定稿：可由 cod_auto_stock_up 控制待确认→备货中）
  → 仓配「发货中」→ 送达/自提核销 → 现场收款完成
```

| 规则 | 约定 |
|------|------|
| 下单 | **直接有效**，跳过「等用户在线付款」 |
| 备货中 | **用户不可自行取消**；取消走在线客服或电话管理员（后台取消） |
| 现场付 | 交货时收款；后台标记已收款/完成 |
| 提货码 / 送达核销码 | 下单生成简单码（订单号衍生或 6 位）；**后台或简易 H5 核销页**输码/扫码确认，保证人货一致；不做独立配送 App（定稿 Q3：送达核销码） |

在线支付相关代码：**配置关闭 + 注释/开关隐藏入口，禁止删除**。

#### 10.7.2 打印

- **不做云打印验收**（易联云/飞鹅代码保留，配置关闭或注释调用）。  
- 支持：后台对 **单个订单** 打开配货/配送单据页 → **浏览器打印**；并支持 **下载**（定稿 T4：浏览器另存 PDF + Excel 导出）。  
- **一式字段（一期必做）**：买家、配送区域、电话、SKU/品名、区域成交价（**本位币为主**）、数量、备注；生鲜单附加产地/冷链/保质期（有则打）。  
- 去掉无用国内快递面单依赖；多联不强制。  
- 定稿补充：批量打印 + 拣货汇总单；打印语言可选 vi/zh/双语（默认 vi）。

#### 10.7.3 通知

- 用户下单 → **管理端即时感知**（简单方案：后台订单列表轮询 / 浏览器通知 / 现有管理员消息加开关）。  
- 不接 Zalo 官方推送 API（本期）；定稿 Q12：一期仅后台页面提醒；Telegram Bot 作为后续可选。

#### 10.7.4 税率

- **商品级税率字段，默认 0**；展示「含税/未含税」有余力再做。不做复杂价税分离引擎。

#### 10.7.5 订单审计（优先复用）

现网已有 **订单操作记录表** `eb_store_order_status`（`oid` / `change_type` / `change_message` / `change_time`）及 `StoreOrderStatusServices`，下单、发货、收货等已在写流水——**这就是订单侧公共审计能力，优先最小扩展复用，不新建审计中台。**

| 项 | 约定 |
|----|------|
| 记什么 | 状态变更（备货中/发货中/取消/完成/已收款等）；重要事项（生成/核销提货码、后台改备注、打印操作可选） |
| 记谁 | 现表**无操作人字段**；最小加列如 `operator_id`、`operator_type`（admin/user/system）、`operator_name`（冗余展示名），旧数据可空 |
| 怎么写 | 抽一薄封装（如 `OrderAuditServices::record($oid, $type, $message, $operator)`），内部仍写入 `store_order_status`；所有状态变更入口统一调用，避免漏记 |
| 怎么看 | 复用/增强后台订单详情「状态变更/操作记录」列表，展示时间、操作人、类型、备注 |
| 不做 | 不另起 `eb_audit_*` 全局表（除非后续多模块强需求）；`SystemLog` 偏接口访问日志，**不替代**订单业务审计 |

状态变更与审计写入同一事务路径，保证「改了状态必有一条审计」。

### 10.8 已确认版 · 联系方式 / 协议 / 改动纪律

#### 10.8.1 联系方式

- **数据字典/系统配置**：类型如 Zalo / 微信 / 电话 / 邮箱等。  
- **配了才展示**；未配置的类型不出现在 H5。  
- 每项字段建议：`type`、`account`（号码/账号）、`qrcode_url`（可选）、`sort`、`status`。  
- **二维码 = 运营独立上传的图片**（走素材库/附件上传，存图片 URL）。  
  - **不是**用账号字符串调用组件「系统生成」的二维码。  
  - 前端只做 `<image :src="qrcode_url">` 展示；无 `qrcode_url` 则只展示账号/可拨打/可复制。  
  - 文档与后台文案写明「上传二维码图片」，避免与订单提货码、分享海报等**系统生成码**混淆。

#### 10.8.2 协议 / 文案多语

| 现状 | 说明 |
|------|------|
| 后台协议 | `AgreementServices` + 类型 type，库内标题/HTML，偏单语 |
| 部分 App 静态 | 如 `pages/columnGoods/static/yhxy.html`、`yszc.html` |
| 界面词条 | DB `lang_code` + uni-app i18n |

**本期建议（简单）：**

1. **界面按钮/提示**：继续走现有 `lang_code`（必要）。  
2. **用户协议/隐私等长文**：采用 `template/uni-app/static/agreements/{zh-CN|vi-VN|en-US}/privacy.html`（用户协议同理）**分语言静态文件**；入口按当前 locale 打开对应文件。改文案发 H5 即可，不必一期做成后台富文本三语。  
3. 若希望运营可改：二期再给协议表加 `lang` 字段；本期不阻塞。  
4. 原单语协议逻辑保留，用开关决定「读静态多语目录」还是「读旧接口」。

#### 10.8.3 改动纪律

### 10.10 已确认版 · 一期必做优化项摘要 + 风险补充

**原「额外优化建议」已升为一期必做（摘要）：**

1. 开放销售区域白名单  
2. 定位失败 → 热门城市兜底  
3. 提货码核销页（后台或简易 H5）  
4. 打印模板一式必要字段（含生鲜附加）  
5. 「允许全国价」生鲜默认关、标品可开  
6. 管理端中文、前台中越英  

| 风险 | 缓解 |
|------|------|
| 分层取价与兄弟区串价 | 单一取价服务 + 单测（区有价/仅市价/仅国价/全国价开关） |
| 切区购物车错价 | 切区清空购物车 |
| 区划数据不准 / 可选节点过多 | **销售区白名单** + 导入后人工改 |
| 定位失败卡首屏 | **热门城市列表**兜底 |
| 下单即有效被刷单 | 定稿 Q5：同 IP/手机号限频 + 后台黑名单 + 订单「需电话确认」标记 |
| 备货中不可取消导致客诉 | 后台取消入口明显；联系方式露出电话/Zalo（上传码） |
| 状态改了无据可查 | **复用 store_order_status + 操作人字段**，变更必记 |
| 联系二维码与系统码混淆 | 后台文案与实现均限定为**上传图片 URL** |
| 多币种与区域价纠缠 | **只存本位价**；展示层换算；订单快照汇率 |
| 现场收款看错币种 | 打印/后台主显示本位币（VND）；展示币仅辅助 |
| 生鲜字段运营乱填 | `is_fresh` 控制表单；核心字段结构化，不单靠自由参数 |
